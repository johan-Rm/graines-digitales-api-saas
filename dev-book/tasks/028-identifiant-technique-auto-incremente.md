# Task : ID technique auto-incremente et UUID public

## Metadonnees

- ID : TASK-028
- Source : strategie d'identification API — ID interne sequentiel + UUID public — 2026-06-15
- Statut : A faire
- Perimetre : entites Doctrine exposees ou relationnelles, trait d'identite, migrations,
  relations internes, providers/processors project-scoped, tests d'isolation
- Dependances fonctionnelles : aucune

## Objectif

Mettre en place une strategie d'identification hybride :

- un `id` numerique auto-incremente comme cle primaire technique interne ;
- un `uuid` conserve comme identifiant public des ressources exposees par l'API.

Le comportement actuel des UUID doit etre conserve cote API : les routes, IRIs et payloads
publics qui utilisent deja l'identifiant UUID ne doivent pas changer de comportement visible.
L'ajout vise principalement les performances internes PostgreSQL/Doctrine : index plus
compacts, jointures plus efficaces, relations internes plus sobres et ordre sequentiel de
creation.

## Contexte technique actuel

Le trait `UuidIdentity` porte aujourd'hui l'identite Doctrine :

```php
#[ORM\Id]
#[ORM\Column(type: 'uuid', unique: true)]
private Uuid $id;
```

Les tables principales et leurs relations utilisent donc des UUID comme cles primaires et
cles etrangeres. La cible est de separer explicitement :

- l'identite technique Doctrine/base (`id`, entier auto-incremente) ;
- l'identite publique/API (`uuid`, UUID v7 genere cote serveur).

Le projet etant encore en cours de developpement, la migration peut partir d'une base vide.
Il n'est pas necessaire de prevoir un backfill de donnees de production existantes dans
cette V1.

## Decisions de cadrage

1. `uuid` reste l'identifiant public et conserve son comportement fonctionnel actuel.
2. `id` devient la cle primaire Doctrine des entites concernees.
3. Les relations Doctrine et les tables de jointure utilisent les IDs numeriques internes.
4. Les clients API ne doivent pas recevoir ni fournir l'ID technique comme identifiant de
   ressource.
5. Les operations project-scoped continuent de passer par les providers/processors
   existants et par `ProjectAccessGuard`.
6. La V1 part d'une base vide : pas de strategie de migration progressive ni de backfill
   des UUID/relations existants.

## Perimetre

### Identite des entites

- Remplacer ou scinder `UuidIdentity` pour obtenir une identite hybride reutilisable.
- Ajouter un `id` technique :
  - type PHP `?int` ou `int` selon l'idiome Doctrine retenu ;
  - `#[ORM\Id]` ;
  - `#[ORM\GeneratedValue]` ;
  - colonne PostgreSQL `INT GENERATED BY DEFAULT AS IDENTITY` ou equivalent Doctrine.
- Conserver un `uuid` public :
  - type `Uuid` ;
  - `#[ORM\Column(type: 'uuid', unique: true)]` ;
  - genere cote serveur en UUID v7 ;
  - expose dans les groupes de lecture lorsque l'identifiant public doit etre visible ;
  - jamais writable depuis le payload client.

### API Platform

- Verifier comment API Platform resout les identifiants publics apres le changement de cle
  primaire Doctrine.
- Maintenir les routes existantes basees sur UUID lorsque c'est le comportement deja expose.
- Si necessaire, declarer explicitement `uuid` comme identifiant API Platform pour les
  ressources publiques, tout en gardant `id` comme cle primaire Doctrine.
- Ne pas exposer l'ID technique dans les IRIs, les URLs publiques ou les payloads clients.

### Relations Doctrine

- Adapter les `ManyToOne`, `OneToMany`, `ManyToMany` et tables de jointure pour pointer vers
  les IDs numeriques internes.
- Verifier les entites project-scoped :
  - `Project`
  - `ProjectMember`
  - `Organization`
  - `OrganizationMember`
  - `User`
  - `CategoryCode`
  - `WebPage`
  - `Article`
  - `MediaObject`
  - `Accommodation`
  - `AccommodationTranslation`
  - `AccommodationMedia`
  - `AccommodationComponent`
  - `AccommodationComponentTranslation`
  - `PropertyValue`
  - `Message`
- Inclure les ressources non exposees directement si elles participent a des relations
  internes critiques.

### Migrations

- Generer une migration coherente avec une base vide.
- Les tables creees doivent utiliser `id` numerique en cle primaire.
- Les colonnes `uuid` doivent etre uniques.
- Les FKs doivent pointer vers les colonnes `id` techniques.
- Les tables project-scoped doivent conserver un index sur `project_id`.
- Les migrations restent reversibles, meme sans contrainte de donnees existantes.

## Validation attendue

- Les entites concernees possedent un `id` technique auto-incremente et un `uuid` public.
- Doctrine utilise les IDs numeriques pour les cles primaires, FKs et tables de jointure.
- Les UUID continuent d'etre generes cote serveur.
- Les UUID restent non modifiables depuis les payloads clients.
- Les routes/API existantes qui exposent des UUID restent compatibles.
- Les endpoints project-scoped ne permettent toujours aucun acces inter-projets, meme avec
  un UUID valide d'un autre projet.
- `project_id` reste indexe sur les tables project-scoped.
- La migration passe sur une base vide.
- Les schemas publics ne changent que si l'API expose effectivement un nouveau contrat.

## Tests a prevoir

- Creation d'une ressource API : `id` interne genere, `uuid` public genere.
- Lecture d'une ressource par son identifiant API public existant.
- Refus ou absence d'effet si un payload tente de fournir/modifier `uuid`.
- Isolation inter-projets conservee lors d'un acces par UUID.
- Relations imbriquees ou jointures principales fonctionnelles apres passage aux FKs
  numeriques.
- Validation Doctrine schema OK sur base vide.

## Points de vigilance

- Le changement de cle primaire Doctrine est structurel : il peut impacter les IRIs API
  Platform, les providers, les denormalizers de relations et les tests fonctionnels.
- Les UUID reduisent l'enumeration des ressources, mais ne remplacent jamais
  `ProjectAccessGuard`.
- Les routes `/api/projects/{projectId}/...` ne doivent pas accepter un `project_id` issu
  du body.
- Les relations internes gagnent en performance seulement si les FKs basculent bien vers
  les IDs numeriques, pas si l'ID est ajoute sans etre utilise par Doctrine.
